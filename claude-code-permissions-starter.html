Claude Code permissions: a starter allow and deny list

Permission rules decide what Claude Code may do without asking. They are short, they live in a JSON file, and they are enforced by the program, not by the model.

The three lists

  • allow: runs without a prompt.
  • ask: always prompts, even if an allow rule also matches.
  • deny: blocked.

They are checked in the order deny, then ask, then allow, and the first match wins. Two consequences: a broad deny cannot be undone by a narrower allow, and a deny in any settings file beats an allow in another one.

Where the rules go

  • ~/.claude/settings.json: yours, for every project.
  • .claude/settings.json: the project's, safe to commit so the team shares it.
  • .claude/settings.local.json: yours, for this project only. Not for committing.

Type /permissions in a session to see every rule and which file it came from.

A starter list

{
  "permissions": {
    "allow": [
      "Bash(npm run build)",
      "Bash(npm run test *)",
      "Bash(git commit *)"
    ],
    "ask": [
      "Bash(git push *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)"
    ]
  }
}

Read it line by line. Build and test run freely. Commits run freely. A push always stops and asks. The .env file and the secrets/ folder are off limits to Claude's file tools.

How the patterns work

  • A bare name such as Bash matches every use of that tool. With parentheses it matches one kind of use.
  • For Bash, * matches any text, spaces included. Put it after the subcommand: Bash(git log *) allows only git log, while Bash(git *) allows every git command.
  • A rule with no * matches that exact command only.
  • File rules take paths: Read(./.env), Read(./secrets/**). Web fetches take a domain: WebFetch(domain:example.com).

Modes are a separate switch

Rules say what is allowed. The mode sets how often it asks. The names are default (asks on first use of each tool), acceptEdits (accepts file edits in the working directory), plan (explores and reads, does not edit your files), auto, dontAsk (refuses anything that would prompt) and bypassPermissions. Set a starting mode with defaultMode. Keep bypassPermissions for containers and throwaway virtual machines, where a mistake cannot reach anything you care about.

What rules do not do

  • A line in CLAUDE.md is not a rule. It shapes what Claude tries. Only a rule in settings changes what is allowed.
  • A Bash deny is not airtight. It does not match the same program called by another route, for example git -C . push against a rule for git push, or a command wrapped in sh -c. Treat rules as a seatbelt. For anything that must not happen, add a sandbox or keep the credential out of reach.
  • A .claudeignore file does nothing. Move its entries into Read deny rules.
  • Syntax changes between versions. A rule Claude Code cannot use is skipped with a warning at startup, and claude doctor shows your resolved settings, so check after editing.

Check it works

  1. Add the rules to .claude/settings.local.json in a scratch project first.
  2. Run /permissions and confirm each rule is listed.
  3. Ask for something each rule should stop, and something it should allow. Both should behave.
