Claude Code glossary in plain words

The Claude Code documentation is full of terms that assume you already know them. This is a short glossary in everyday language, grouped by what you are trying to understand. Where we have a longer guide on a term, it is linked.

How it works

  • Agentic coding. Claude can read files, run commands and edit code on its own while you watch or step away, instead of only answering with text you have to apply yourself.
  • Harness. Everything around the model that makes it a coding agent: file access, running commands, asking permission, loading memory, and the loop that chains steps together. Claude Code is the harness; Claude is the model inside it.
  • Agentic loop. The cycle Claude repeats on every task: gather context, act, check the result, repeat until done. You can interrupt at any point. See how Claude Code works.
  • Tool. One action Claude can take: read a file, edit code, run a shell command, search the web, start a subagent. Without tools it could only talk.
  • Turn. One full response from Claude, from your message to the moment it finishes, with any number of tool calls in between.
  • Session. A conversation tied to your current directory, with its own context window. You can resume it, fork it, or run several in parallel. /clear starts a new one and the old one stays stored.
  • Transcript. The saved record of a session, kept as a file so a conversation can continue after you close it.

Memory and context

  • Context window. Claude's working memory for the session: the conversation, file contents, command output, your instructions and loaded skills. It fills up as you work. /context shows what is using space.
  • Compaction. When the context window nears its limit, the conversation is summarized automatically; /compact does it on demand. Instructions you only gave in chat may not survive. See what survives compaction.
  • CLAUDE.md. A markdown file of standing instructions you write, loaded at the start of every session. See CLAUDE.md, skill or hook.
  • Auto memory. Notes Claude writes for itself from your corrections and preferences. The counterpart of CLAUDE.md, which you write. See the memory guide.
  • Rules. Extra instruction files in .claude/rules/. A rule can be tied to certain file paths so it only loads when Claude touches those files.
  • System prompt. The built-in instructions sent ahead of your conversation on every request. Your CLAUDE.md and output style are not part of it; they arrive inside the conversation.
  • System reminder. A note the harness adds to the conversation to give Claude context, such as your CLAUDE.md, the list of skills, or a warning that a file changed on disk. You do not send these yourself.
  • Checkpoint. A restore point made at each prompt that starts a turn. Esc twice or /rewind goes back to one. See undoing changes with rewind.
  • .claude directory. Where project settings, hooks, skills, subagents, rules and memory live. Your personal defaults live in ~/.claude/. See the .claude folder explained.

Control and safety

  • Permission mode. The baseline approval behavior for the session, cycled with Shift+Tab. See permission modes.
  • Permission rule. A settings entry that allows, asks about or blocks a specific tool use. Rules sit on top of the mode. See a starter set of permissions.
  • Plan mode. A permission mode where Claude researches and proposes a plan without editing your files, then waits for approval.
  • Auto mode. A permission mode where a separate model reviews actions instead of you, so most run without a prompt. It still asks where your own ask rules match.
  • Sandboxing. Operating-system limits on what shell commands can touch, so Claude can work freely inside a boundary. A separate layer from permission rules. See the sandbox guide.
  • Project trust. The dialog where you accept a folder before Claude Code loads the configuration it ships with.
  • Prompt injection. Hostile instructions hidden in a file, web page or tool result that try to steer Claude toward things you never asked for. The permission system and trust checks are part of the defence.
  • Settings layers. The order Claude Code reads configuration in, from organization policy down to your user file. See which settings.json wins.
  • Managed settings. Settings an organization enforces for everyone. Users and projects cannot override them.

Extending it

  • Skill. A SKILL.md file with instructions or a workflow Claude loads when relevant, or when you type /skill-name. As we read the docs, skills are the recommended successor to custom commands. See how to write one.
  • Command. A reusable instruction you run by typing /name. The word is also used for CLI subcommands like claude mcp add, which are unrelated.
  • Frontmatter. The block of settings between two --- lines at the very top of a Markdown file. Skills, subagents, output styles and rules read their configuration from it.
  • Hook. A handler that runs automatically at a fixed point, such as before a tool runs or after a file edit. It fires every time, not when the model feels like it. See three hooks to paste.
  • Subagent. A specialized assistant with its own context window, prompt and tool access, which does a delegated job and reports back a summary. See writing one.
  • Agent teams. Several separate sessions coordinated by a lead, each with its own context. Unlike subagents, you can talk to any of them directly. The docs describe this as experimental and off by default.
  • MCP and MCP server. An open standard for connecting outside tools and data, and a program that provides them to Claude. See adding an MCP server.
  • Plugin. A bundle of skills, hooks, subagents and MCP servers installed as one unit. See installing plugins.
  • Output style. A setting that changes the instructions Claude gets, to adjust tone or format. See output styles.
  • Bundled skills. Prompt-based playbooks that ship with Claude Code, such as /loop and /debug. See scheduling with /loop.

Running it without you

  • Non-interactive mode. Run one prompt and exit, with -p. For scripts, CI and pipes. Older material calls it headless mode. See running Claude Code from a script.
  • Bare mode. --bare starts without loading hooks, skills, plugins, MCP servers, memory or CLAUDE.md, so a scripted run behaves the same on every machine.
  • Verification loop. Giving Claude a check it can run, such as a test suite or a build, so it keeps going until the check passes instead of stopping at something that merely looks right. It is the groundwork for the /goal command.
  • Worktree isolation. Running Claude in a separate git worktree, so parallel agents each edit their own copy. See worktrees and parallel sessions.

Where it runs

  • Surface. Any place you use Claude Code: the terminal, VS Code, JetBrains, the desktop app or claude.ai. They share one engine.
  • Local session and cloud session. A cloud session runs on cloud infrastructure and keeps going after you close your laptop. A session in your terminal or IDE is local.
  • Remote Control. Continue a local session from your phone or browser. The code and files stay on your machine; only the interface is remote.
  • Teleport. /teleport pulls a cloud session into your local terminal. --cloud goes the other way.
  • Channel. An MCP server that pushes events into a running session, so Claude can react while you are away.
  • Connector. An MCP server added to your claude.ai account instead of configured locally.

Old names you may still meet

  • Headless mode is now non-interactive mode.
  • Custom commands are now skills; older command files still work.
  • Slash commands are now just commands.
  • “Claude Code on the web” as the name for every cloud session has narrowed to the browser surface at claude.ai/code.
